# Harness Engineering：AI 能在真正"出事会炸"的后端系统里写代码吗？

> 来源：https://mp.weixin.qq.com/s/MzB8-B00GVdJy22j42CRgg
> 作者：TRAE
> 标签：Harness Engineering, AI Coding, 后端, 大模型工程

## 核心定义

**Harness Engineering**：除了 LLM 本身之外，让 Agent 真正能干活的一切基础设施。优化模型运行所需的环境、机制与基础设施的总和，一套将 AI 的"智能"转化为可靠、可控、可规模化"生产力"的工程哲学与实践框架。

## 核心挑战：后端的真实复杂度

后端 AI Coding 面临的核心挑战在于**可执行的工程事实**。后端的真实复杂度几乎全部隐藏在接口签名之外：

一次"提交操作"背后涉及：
1. Service 内部的同步 RPC 调用
2. 本地事务控制与回滚逻辑
3. 数据库写入与 binlog 产生
4. 异步链路触发（Kafka、ES、缓存刷新）
5. 跨模块的数据一致性与最终状态收敛

**传统 RAG 的问题**：每次提问都要检索相关片段拼凑，没有积累。

## 三层架构（Harness 本质）

Harness 本质是一个带有边界控制、工具路由与确定性反馈的 **REPL 容器**：

- **Read（读取）**：上下文管理器将外部世界翻译成 LLM 可理解的结构化 Prompt
- **Eval（评估/执行）**：调用拦截器捕获 LLM 生成的规划，路由到正确工具执行
- **Print（打印/反馈）**：反馈汇编器捕获执行结果，重注入供 LLM 反思
- **Loop（循环）**：管理从"感知"到"行动"再到"反思"的完整生命周期

## 代码图谱化

当代码关系以图的形式存在后，AI 不再需要"猜"系统结构。通过图数据库查询，AI 可以明确知道：
- 一个类的上下游依赖
- 一个方法被哪些路径调用
- 一次改动可能影响的范围

**Context 不再只是静态文本，而是结构化、可推理的工程事实。**

## Spec Coding 与 DSL 化

自然语言 Spec 的问题：
- 机器没法校验，歧义还在，跟代码之间没有任何强绑定
- 项目启动那天是准的，三个月后开始漂移，六个月后成了历史文献

**DSL-SPEC**：机器可解析、可校验、可驱动的表达介质。类似 k8s YAML 声明式 DSL 在运维领域的作用。

| k8s YAML | TocoAI DSL-SPEC |
| --- | --- |
| 描述服务的终态 | 描述数据结构的意图 |
| 机器做调度、维持状态 | 引擎生成结构性代码 |
| 人不需要关心如何部署、扩容 | 人不需要关心如何写 Converter、Assembler |
| 变更成本：改 replicas 值，其余不动 | 变更成本：改一个字段，级联自动更新 |

**未来方向**：DSL-Spec 为骨骼（形式化、可校验），NLP-Spec 为血肉（填满只能意会的业务细节）。

## 关键结论

1. **精准的 Context 是后端 AI Coding 的决定性因素**。只有当代码被图谱化、被语义化、被工程化之后，AI 才能真正理解系统级结构。

2. **提升可控性是核心能力**。可控性不是通过更强的模型能力自然获得的，而是由模型能力、Prompt 设计、系统框架与工程校验共同构成的体系化能力。

3. **从"执行者"到"设计者"的角色跃迁**。AI 承担代码编写等具体任务，人类工程师转向系统设计、定义规则、验收成果。
